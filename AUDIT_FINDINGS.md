# Suven-Examination — Production Audit Findings

Date: 2026-07-23
Scope: server.ts, migrate-db.ts, src/, firestore.rules, deploy configs
Goal: improvements without breaking existing functionality

## Status update

Findings #1–#4, #6, #7 below are fixed: session/role middleware (`requireSession`,
`requireRole`) now gates `/api/db/query`, `/api/db/write`, exam/question delete, DB
migrate/seed, and the GCP sync-iam/live-billing routes; a per-collection/per-role ACL with
tenant scoping (`COLLECTION_ACCESS`/`SCOPE_FIELD`) governs the generic DB proxy; Firebase ID
tokens are now cryptographically verified server-side (`/api/auth/validate`,
`/api/auth/create-profile`) instead of trusted from the request body; `firestore.rules`
tightened to deny-by-default; `SyllabusTracker.tsx`'s write UI is now actually gated by role.

Two additional issues found while implementing the fix, not in the original pass, both fixed:

- `PUT /api/exams/:examId` and `POST /api/exams/:examId/import-doc` had the same
  zero-auth problem as the routes above — now gated (session + creator/admin ownership).
- `POST /api/exams/:examId/import-doc` had a **command injection** vulnerability: the
  `examId` URL param was interpolated into a shell command string passed to `exec()`,
  escaped only for double-quotes. Switched to `execFile` with an argument array, which
  never invokes a shell, closing it structurally rather than by escaping.

## Round 2 — role model + scale + two more broken flows found

Per explicit product spec: admin has full access (added the schools, so owns everything);
school is view-only on exams/question papers, manages its own students, and shares exam
links; students validate roll number + name against their school, take the exam, and
results flow back to the school. Tightened `exams`/`questions` writes to admin-only
accordingly (`COLLECTION_ACCESS`, plus the `PUT /api/exams/:id` and import-doc route guards).

**100k-concurrent-students requirement**: the ownership checks added in round 1 did a
synchronous Firestore read before every write — at 100k students autosaving their attempt
every ~30s, that doubles read load on the hottest collection in the app for the whole exam
window. Added an in-memory owner-cache (`ownerVerificationCache`, 30 min TTL, same pattern
as the existing `localSubmissionLocks`) so ownership is verified once per attempt/exam/
question instead of on every write.

**Two more pre-auth flows broken by round 1, both fixed**: both do direct Firestore
reads/writes to `users`/`invitations` _before any session exists_, which round 1's auth
gate on those collections silently 401'd:

- `StudentLinkEntry.tsx` (roll-number entry via a shared `secure_exam_links` link) — the
  "validate roll number against school" lookup/auto-onboard step. Moved server-side into a
  new `/api/gatekeeper/verify-identity` route.
- `LoginPage.tsx`'s separate per-student invite-link flow (`/login?invite=<token>`,
  generated by `SchoolStudentOnboarding.tsx` — the actual "school shares the link" feature).
  Moved server-side into two new routes, `/api/gatekeeper/invite-metadata` and
  `/api/gatekeeper/verify-invite`, which then hand off to the existing `/api/gatekeeper/
enroll` for the actual attempt create/resume/reattempt (reused rather than duplicated).

Both were caught by manually tracing each pre-auth code path against the new ACL rather
than assuming the collection-level rules were sufficient — same class of bug as the
gatekeeper session-minting gap found in round 1's own verification pass.

Remaining items (#5, #8–#15) are unchanged — see below, still "no rush" cleanup, not
security-critical.

Root cause: session tokens are generated but verified only on `/api/auth/session` itself.
Role/permission checks in `src/lib/AuthContext.tsx` are client-side only — trivially bypassed
via direct API calls. One auth middleware fixes the whole security class below.

## SECURITY (fix first)

1. **server.ts:1220-1296** `/api/db/query` — generic Firestore read proxy, zero auth check.
   Any client can read any collection (`users`, `sessions`, etc.) by name. Full data exposure (IDOR).
   Fix (low-risk): add middleware checking `Authorization: Bearer <sessionToken>` against
   `sessions` collection + server-side allowlist mapping `role → permitted collections`.
   Apply only to this route — no change to route contract/shape.

2. **server.ts:1299-1337** `/api/db/write` — same proxy pattern for writes, only guarded by
   dup-submission check, not auth. Any client can write/overwrite any document in any collection.
   Fix: same session+allowlist middleware as #1, scoped to owner/role.

3. **server.ts:2151-2287** `/api/db/migrate` and **server.ts:2290+** `/api/db/seed` — full DB
   migration/reseed triggered by unauthenticated POST. If publicly reachable, anyone can overwrite
   production data. Fix: require admin session token, or gate behind an env-controlled flag
   disabled in prod + IP/admin check.

4. **server.ts:870** `DELETE /api/questions/:questionId` and **server.ts:897**
   `DELETE /api/exams/:examId` — no auth, no role check. Any client can delete exam content.
   Fix: add admin/school-role check middleware, no contract change.

5. **server.ts:42** and **migrate-db.ts:33** — hardcoded Firebase API key (`AIzaSyD-...`)
   committed in source, duplicated in two places. Low individual risk (Firebase web keys aren't
   secret by design) but signals config-in-code habit; pattern repeats for
   `sourceConfigOverride` defaults at **server.ts:2155-2163**. Fix: move to env var with the
   current value as fallback only in non-prod.

6. **firestore.rules:12,17,22** — rules allow `read, write: if true` on everything. Currently
   dormant since the client never talks to Firestore directly (goes through `apiService` → server
   proxy per `src/lib/firebase.ts:13-33`) — but it's the only backstop if anyone ever adds a
   direct Firestore SDK call, or if these keys leak. Fix: tighten rules to deny-by-default now
   while it's free (no functional impact since client doesn't use them today).

7. **server.ts:1577-1591 / 1712-1714** — session tokens generated but never verified by any
   route except `/api/auth/session` itself. This is the root cause of findings #1-4; fixing the
   middleware once and applying it to all mutating/sensitive routes fixes the whole class.

## RELIABILITY / DATA INTEGRITY

8. **server.ts:897-931** — exam delete loops `clientDeleteDoc` one-by-one per question, no
   batching/transaction. Partial failure mid-loop leaves orphaned questions + exam still present.
   Fix: wrap in `clientWriteBatch`, matches pattern already used in migrate route (server.ts:2220).

9. **server.ts:2151-2287** — migrate route has no dry-run/idempotency guard, re-running it
   re-writes every doc unconditionally. Fine for intended one-time use, risky if exposed (ties
   to #3).

10. **server.ts** (2605 lines) — mixes Firestore REST client, route handlers, auth, billing, and
    migration logic in one file. Raises risk that an unrelated edit breaks something else, makes
    the missing-auth issue harder to spot by inspection. Fix (pure refactor, zero behavior
    change): split into `lib/firestoreRestClient.ts`, `routes/*.ts` grouped by domain, keep
    `server.ts` as composition root only.

## MAINTAINABILITY

11. **src/services/api.js** — thin re-export wrapper around `api.ts` (lines 1-41), dead
    duplication, two files to keep in sync for no functional reason. Fix: confirm nothing
    imports `.js` specifically, then delete it.

12. Multi-target deploy config present simultaneously: `Dockerfile`, `docker-compose.yml`,
    `app.yaml` (GCP App Engine), `cloudbuild.yaml`, `vercel.json`, `firebase-blueprint.json`.
    Confirm with the team which is actually live — unused ones are cruft and a source of config
    drift (e.g. stale env var lists diverging from `.env.example`).

13. **server.ts** has 13 `console.log`/error calls, no structured logging/log levels. Fine at
    current scale, makes prod log triage harder as traffic grows. Low priority.

## PERFORMANCE

14. **src/components/ExamInterface.tsx** (1836 lines) — only 20 combined
    `useMemo`/`useCallback`/`React.memo`/`useEffect` hits across a file this size. Worth
    profiling for unnecessary re-renders during active exam-taking (timer ticks, answer
    updates), since this is the highest-traffic, highest-stakes screen. Not a confirmed bug,
    just a hotspot worth profiling before assuming it's fine.

15. **server.ts:1226-1288** — in-process `queryCache` (Map, per-instance). Fine for single
    instance, but if deployed with >1 replica (Docker/Cloud Run scale-out), cache is
    inconsistent across instances. Redis is already wired in for rate-limiting (server.ts:658)
    but not reused for this cache. Low priority unless multi-instance is the actual prod
    topology — worth confirming.
